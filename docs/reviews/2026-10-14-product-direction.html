02 / My product take

The moat is continuity and trust.

“We can stop tonight and pick up tomorrow. Nobody loses their place. When it ends, there’s a story of our game.”

That is the product promise I would build around. The architecture already supports much of it: permanent account ownership, frozen historical names, durable tables, versioned rules, correction-aware history and forgiving Undo. These are unusually useful foundations for a casual social game.

The main product risk is breadth outrunning clarity. Browser, Android, camera, BLE, Pi and custom dice are substantial workstreams; the player should encounter a simple sequence: find the table, take a turn, trust the save, return later. I would mature that manual journey before expanding the sensing experience.

Give the table an identity

Tournament name, original players, game number, pause state and next turn should form one recognizable header across lobby, play, return and results.

Use one clear returning-user route

“Continue your table” becomes the dominant home action. Host and Join stay easy to find. History belongs behind the same table hub.

Keep score entry dominant

The next category is the main interaction. Rules explanations, optional combination reports and charts should not become extra mandatory steps.

Celebrate things we can prove

Personal bests, upper bonuses, a close finish and shared winners are meaningful. Physical timing and roll success rates need data that manual scoring does not collect.

Positioning hypothesis:

A friendly recurring game night companion for couples, families and small groups. Validate that with returning players before choosing pricing, broad audience acquisition or a hardware-led commercial offering.

03 / Artistic direction

Warm, calm, unmistakably yours.

Keep the existing dark clubhouse palette: deep slate, mint for the next action, lavender for personal achievements and amber for paused or important states. Give names and game progress more space. Reserve celebratory movement for accepted achievements, with reduced-motion support.

03. A recap worth keeping

Two equally legible standings, real game moments and an optional keepsake export. Shared wins remain explicit when there is a tie.

Observed in source

Two changes with immediate value

A paused guest card currently says “Resume tournament”; the actual action opens a table that waits for its host. Change the promise to “Open saved table.”

The online home exposes Resume plus older tournament and online-game lists. Consolidate the player-facing routes after checking their compatibility responsibilities.

Research-informed proposal

Small controls, fewer doubts

Show confirmed / saving / reconnecting states. Put a readable build identifier in Help. Offer an update at a safe boundary when appropriate; preserve unfinished input and account data.

Use large tap areas, text alongside state color, visible focus and password-manager/paste support. Treat accessibility as a tested behavior. W3C target guidance, authentication guidance.

New idea

“Since you were away”

A compact return summary: accepted scores, host pause/resume, or next-game start since your last acknowledged revision. Derive it from authoritative history. Avoid revealing hidden totals or treating “seen” as gameplay authority.

New idea

The tournament keepsake

A local export with both champions, game-time aliases, results and three verifiable moments. Make sharing optional. Explore seasonal friendly leagues only after small-group retention and tournament completion are demonstrated.

04 / Proposed sequence

Earn trust. Explain history. Grow the clubhouse.

These are proposed stages, not committed dates or newly authorized deployments. Each is a bounded increment with its own evidence. Baseline reconciliation can proceed alongside acceptance preparation.

01

Accept the current manual journey

Immediate

Confirm SW-019 on Android and the existing iPhone client. Test own Undo, next-player race, partial tournament pause/return, original-link rejoin and Competition v2 final-chain behavior using original accounts.

Exit evidence: both screens agree on room/game/seat/turn; guest can return before host; pause remains until explicit host resume; stale Undo cannot erase a later score; no reset, account clearing or accidental new roster. Record actual build, mode, phase and symptom for each failure.

02

Make updates and return understandable

Next bounded UX slice

Reproduce cached-client behavior before selecting a lifecycle fix. Add useful version/update visibility and role-correct saved-table labels. Prototype the consolidated home rather than redesigning every screen at once.

Exit evidence: already-installed Safari browser and Home Screen clients activate the intended build without data clearing; pending entry survives; pause/return authority is unchanged. Two-, four- and eight-player phone layouts, zoom/text scaling, focus and reduced motion are checked.

03

Establish a reproducible software baseline

Parallel preparation

Reconcile the preserved dirty tree into reviewable scoped source changes. Identify supported inputs, clean setup and exact artifacts. Verify remote CI and enforcement as deployed configuration, rather than assuming local workflow files establish them.

Exit evidence: pre-existing work is preserved, supported clean setup and Node24 configured gate pass, source/build manifests agree, optional camera omissions are declared. No automatic staging, pushing or release decision is implied by this review.

04

Ship the game story and easier invitations

Separate small increments

Start with read-only per-game chronology and account-owned history. In a separate slice, improve invitation preview/share and sign-in/verification destination return. Keep frozen historical names; nickname edits affect future game snapshots.

Exit evidence: UUID-owned paging discovers older history; score/correction/Undo displays reconcile with final sheets; undone scores do not count as achievements; hidden totals remain private. Invitation verification/recovery returns to the exact table; full/expired invitations are actionable; no duplicate membership.

05

Add useful, comparable insights

After projection contracts

Build account trends and tournament encouragement using pure history projections. Separate mode/rules versions. Show both champions and shared wins. Prioritize best comparable game, upper-bonus count and category patterns over a wall of charts.

Exit evidence: corrections, Undo, reopened completion, ties and changed aliases have meaningful fixtures; account views agree across devices; exports reconcile. Define any “first/late” achievement as scoring order. Never backfill invented physical timestamps or decision speed.

06

Trial optional combinations, then a wider pilot

Later / evidence-led

Add a lightweight “I rolled…” logger separate from scoring, including already-filled categories. Follow with a small recurring-group pilot and support/update/privacy readiness. Keep camera, BLE and custom-dice qualification separately planned.

Exit evidence: combination reports alter no score, turn or bonus, have account ownership/idempotent retries and explicit self-reported labels. Distinguish logging completeness from actual roll frequency. Pilot records return failures and completed journeys; applicable independent reviews and owner acceptance remain named open gates.

Suggested pilot measures, not accepted numerical targets:

Invitation-to-join completion, successful return to the same partial table, update failures, tournament completion and voluntary second game night. Measure only with an agreed collection/privacy plan; no tracking has been added. Agree thresholds with the product owner before pilot qualification.

05 / Lead developer approach

Keep the strong boundaries. Reduce integration risk.

Preserve the core and authority

Immutable scoring/rules remain pure. The server owns authenticated seat, exact game, revision and transactional persistence. Views consume state and projections. The generated Supabase function is built from server source.

Avoid a framework rewrite for its own sake. Extract new history/analytics modules behind agreed contracts while integrating shared UI changes sequentially.

Build one history projection contract

Retain every audit event, but derive awards from corrected non-undone scores and eligible finished games. Use game-time aliases for display and UUID for identity. Event array order currently provides chronology; do not assume an explicit sequence field exists.

Keep legacy two-player/name-keyed statistics isolated. Do not retrofit their identity or elapsed-time assumptions into multi-day hosted games.

06 / Evidence and research

Facts, observations and proposals stay distinct.

Project evidence

14 October handover, status, software control, SW-019 manifest, SW-017 scope and focused source review. These establish recorded development state, not fresh live connectivity.

Service-worker lifecycle

web.dev lifecycle: refresh can leave an updated worker waiting; immediate activation can mix old pages with a new worker. Investigate the actual client lifecycle before choosing an update policy. This is a plausible diagnosis, not a proven cause of the recorded stale tab.

Touch and accessible authentication

W3C target size: WCAG 2.2 AA uses 24×24 CSS pixels or qualifying exceptions. A 44px product touch target is a stronger design preference, not that AA requirement. W3C authentication supports assistance such as password managers and paste.

Native sharing

MDN Web Share API: availability varies and sharing requires user activation. Provide copy/QR fallback. The chooser does not establish email delivery or imply permission for automated sending.

My recommendation:

Close the real return/Undo/update acceptance loop first. Then make the table easier to find, invitations easier to complete and history easier to understand. Let hardware and richer analytics expand a product players already trust.
