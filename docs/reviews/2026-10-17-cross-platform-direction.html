01 / COMPOSITION

Useful space earns its place.

Own score first. A smaller opponent reference. Context in one line. Full stats live a tap away; they don’t push the game off the screen.

02 / VISUAL LANGUAGE

Confidence without decoration.

Warm paper, ink, cobalt and coral. Player names and compact data marks. No avatars, casino palette or character-led branding. “Matchday” is a working design label.

03 / MOTION WITH MEANING

Make the changing game visible.

A score settles into its frame. The bonus target fills. A lead line crosses. A comeback becomes a streak. Save the strongest treatment for a secured bonus or tournament title.

No looping spectacle, forced waiting or celebration before the server accepts a score. Optional sound and haptics; a complete quiet mode.

Native delivery

Yes to an iOS app.

A signed installed app improves launch, links, audio integration and platform control. It does not require a separate SwiftUI scorecard. Build once at the presentation layer, with deliberate platform adapters.

Graphics choice

SVG first. PixiJS where earned.

Our game is a rich scorecard and a competition, rather than a physics world. Keep text and scoring accessible. Use GPU effects for bounded visual moments only when the prototype proves a need.

Multiplayer

Either phone can organise.

iPhone and Android create, host and join the same manual tournaments. The server owns the game state. Closing the organiser’s phone doesn’t erase the table. Hardware capabilities remain a separate track.

PlatformArchitect’s assessment
Capacitor + React / TSRecommended. Retains current rules, backend and browser participation. New shared UI with native iOS/Android adapters.
Phaser + CapacitorA good 2D game framework if virtual dice, scenes or minigames become central. More game machinery than this scorecard currently needs.
Flutter / FlameStrong alternative for a fresh client. More rebuilding of the UI, client integrations and storage; less reuse of the working application.
React NativeStrong native approach; existing DOM/SVG UI needs replacement and browser parity needs additional care. Revisit if a native-only product becomes the priority.
Godot / UnityReconsider for an immersive 3D table or physics-led game. That would be a different product investment.

Prove, design, then migrate.

Six stages · each has a reviewable exit

Rough planning range: 8–12 weeks for a small team with design, shared-client and native/backend capability, plus prompt feedback. These are estimates, not commitments. Apple enrolment/review delays and hardware work are outside this range.

01 / DIRECTION + RISK

Approve it on two phones.

Refine this visual territory and motion. Prove signed iOS startup, account return and the risky voice transport. Confirm or revisit the stack from measured results.

02 / SHARED FOUNDATION

Build the new application shell.

React/TS components, design tokens, room and native adapters. Preserve existing rules, accounts and storage. Keep the current app available during migration.

03 / THE SCORING SLICE

Make one turn excellent.

Centred scoring, upper bonus, scratches, latest-frame Undo, clear pending/accepted feedback. No animation or speech blocks a score.

04 / TOURNAMENT STORY

Make the stakes visible.

Exact comeback and clinch scenarios. Wins and points races. Accepted-score replay, records and meaningful trends, including ties and corrections.

05 / PLATFORM PARITY

Swap who hosts.

Amber hosts on iOS; Keith joins Android. Reverse it. Add Safari. Verify invitations, reconnection, lifecycle and optional native iOS voice.

06 / RELEASE CANDIDATE

Play complete tournaments.

Physical-device performance, accessibility, interruptions and data-preserving upgrades. Android build, TestFlight beta and web release with rollback evidence.

What is involved in iOS alone?

Allow 3–5 engineer-days for the risk spike, approximately 10–15 engineer-days for a current-UI manual multiplayer TestFlight beta once the Mac/signing setup is ready, and 5–10 additional days for voice parity. These overlap the roadmap; don’t add every estimate together.

We need Mac/Xcode build access and Apple signing/TestFlight setup. The current Android audio plugin needs an iOS implementation; adding an iOS shell is not enough. BLE/camera parity is separate and must not hold up manual cross-platform games.

App Store readiness also includes privacy, account flows and review. No store approval or performance target is established by this study. Your working build and tournament remain unchanged.
